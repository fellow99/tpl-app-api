# 整体规格文档

> 项目：tpl-app-api（tpl-workspace 后端 — 用户侧 API）
> 状态：已实现
> 最后更新：2026-08-22
> 范围：系统级功能规格（技术无关）

---

## 1. 系统概述

### 1.1 系统目的

tpl-workspace 后端 API（tpl-app-api）是一个面向用户的 RESTful API 服务，提供用户注册、登录认证、个人中心等核心功能。该服务是 "tpl-workspace" 产品体系的用户侧入口，与前端应用（tpl-app-web）配合，为用户提供账号管理体验。

### 1.2 目标用户

- **用户**：使用前端应用注册账号、登录系统、管理个人信息
- **管理后台**（tpl-manage）：通过共享数据库管理用户数据，但与本系统无直接 API 交互

### 1.3 系统边界

**在范围内**：
- 用户注册（含图形验证码）
- 用户登录（签发 Token，支持密码/短信/微信）
- 用户登出
- 获取图形验证码
- 个人中心（查看/修改信息、修改密码）

**不在范围内**：
- 角色/权限管理（RBAC）— 由 tpl-manage 管理后台负责

## 2. 核心能力

### US-001：用户注册

> 作为用户，我可以注册一个账号，以便使用 tpl-workspace 的功能。

**验收标准**：
- 用户提供用户名、密码和验证码
- 系统校验用户名唯一性、验证码正确性
- 注册成功后系统创建用户账号和个人档案

### US-002：用户登录

> 作为已注册用户，我可以登录系统，以便访问需要身份认证的功能。

**验收标准**：
- 用户提供用户名、密码和验证码
- 系统校验密码正确性和账号状态
- 登录成功后系统返回访问令牌（Token）
- Token 在 30 天内有效（可配置）

### US-003：用户登出

> 作为已登录用户，我可以登出系统，以使当前会话失效。

**验收标准**：
- 已登录用户请求登出
- 系统使当前 Token 失效

### US-004：获取验证码

> 作为用户，我可以在登录或注册时获取图形验证码，以证明非机器人操作。

**验收标准**：
- 系统生成 4 位字符的图形验证码图片（Base64 编码）
- 验证码有效期为 5 分钟
- 每个验证码只能使用一次

### US-005：个人中心

> 作为已登录用户，我可以查看和管理我的个人信息。

**验收标准**：
- 已登录用户请求个人信息
- 系统返回该用户的账号与档案信息

## 3. 功能需求

### 3.1 用户认证

- FR-001-001：系统 MUST 接受用户名、密码和验证码作为注册参数
- FR-001-002：系统 MUST 验证用户名在系统中唯一
- FR-001-003：系统 MUST 使用 BCrypt 哈希算法存储密码
- FR-001-004：系统 MUST 在注册成功后同时创建用户基本信息（sys_user）和个人档案（user_profile）
- FR-001-005：系统 MUST 在校验密码时使用 BCrypt 比对
- FR-001-006：系统 MUST 在校验通过后签发 JWT 令牌
- FR-001-007：系统 MUST 检查用户状态，停用用户（status=1）MUST NOT 被允许登录
- FR-001-008：系统 MUST 支持通过配置项（captcha.enable）全局开关验证码校验

### 3.2 验证码

- FR-001-009：系统 MUST 生成 4 位字母数字混合的图形验证码
- FR-001-010：验证码 MUST 存储于缓存系统（Redis），有效期为 5 分钟
- FR-001-011：验证码 MUST 一次性消费，校验后立即删除
- FR-001-012：验证码校验 MUST NOT 区分大小写

### 3.3 会话管理

- FR-001-013：系统 MUST 在登录时签发 Token，Token 有效期默认为 2592000 秒（30 天）
- FR-001-014：系统 MUST 支持用户主动登出（Token 作废）
- FR-001-015：除明确放行的路径外，所有 API 请求 MUST 携带有效 Token

### 3.4 个人中心

- FR-002-001：系统 MUST 提供接口查询当前登录用户的账号与档案信息
- FR-002-002：系统 MUST 提供接口修改个人信息（昵称、邮箱、生日）
- FR-002-003：系统 MUST 提供接口修改密码

### 3.5 公共规范

- FR-000-001：所有 API 响应 MUST 使用统一格式 {code, msg, data}
- FR-000-002：成功响应 code MUST 为 200
- FR-000-003：业务异常 MUST 返回 code=500 及中文错误描述
- FR-000-004：系统 MUST 支持跨域请求（CORS），允许所有来源

## 4. 非功能需求

### 4.1 安全

- NFR-S-001：用户密码 MUST 使用 BCrypt 哈希存储，MUST NOT 明文存储
- NFR-S-002：JWT 签名密钥 MUST 在生产环境中配置为强随机字符串（当前使用硬编码值，标记为待改进）

### 4.2 性能

- NFR-P-001：数据库连接池 MUST 使用 HikariCP，最小空闲连接 5，最大 20
- NFR-P-002：Redis 连接池 MUST 使用 Lettuce，最大活跃连接 8

### 4.3 可用性

- NFR-A-001：开发环境 SHOULD 关闭验证码以提高开发效率
- NFR-A-002：系统 SHOULD 通过 Spring Profile 支持多环境部署（dev / docker）

### 4.4 数据完整性

- NFR-D-001：注册操作 MUST 使用数据库事务确保 sys_user 和 user_profile 同时创建
- NFR-D-002：数据删除 MUST 使用逻辑删除（delFlag 字段），MUST NOT 物理删除

## 5. 假设与约束

| # | 假设/约束 | 来源 |
|---|-----------|------|
| A-001 | 数据库 `tpl_manage` 已由 tpl-manage 工程初始化，包含所需表结构 | 系统间依赖 |
| A-002 | `tpl_user_view` 数据库视图已存在，提供用户基本信息与档案的联表查询 | 数据访问层 |
| A-003 | 前端（tpl-app-web）负责 Token 的存储和每次请求携带 | 前后端分工 |
| A-004 | 支持密码/短信/微信三种登录方式 | 产品决策 |
| A-005 | 不做 RBAC 权限模型，所有已登录用户拥有相同的接口访问权限 | 产品决策 |

---

## 6. 依赖系统

| 系统 | 依赖方式 | 说明 |
|------|---------|------|
| PostgreSQL | 数据库 | 用户数据的持久存储 |
| Redis | 缓存 | 验证码临时存储、Sa-Token 会话管理 |
| tpl-manage | 共享数据库 | 管理后台通过同一数据库管理用户 |
| tpl-app-web | HTTP 调用方 | 前端应用，本 API 的唯一消费者 |

---

## 7. 术语表

| 术语 | 定义 |
|------|------|
| Token | 用户登录后的访问凭证，通过 HTTP Header `Authorization` 传递 |
| 验证码 (Captcha) | 4 位图形验证码，用于防止自动化攻击 |
| 逻辑删除 | 通过设置 `del_flag='1'` 标记删除，而非物理删除记录 |
